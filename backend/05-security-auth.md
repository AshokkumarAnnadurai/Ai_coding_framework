# Backend Standards: Security & Authentication

Rules for authentication, authorization, credential handling, input sanitization, secret management, and pre-implementation security review.

## 1. Authentication & Authorization

*   **Use Framework-Provided Mechanisms First:** Prefer NestJS's built-in and ecosystem-standard tools — `@nestjs/passport`, `@nestjs/jwt`, Guards, and custom decorators — over hand-rolled auth logic. These are audited, well-understood, and reduce the odds of introducing a subtle vulnerability.
*   **Guards for Authorization:** Gate protected routes with `@UseGuards(AuthGuard('jwt'))` (or session equivalent) plus a `RolesGuard` driven by a `@Roles(...)` decorator for role/permission checks. Do not reimplement token verification inline inside controllers.
*   **`@CurrentUser()` Decorator:** Extract the authenticated user via a custom parameter decorator rather than reaching into `request.user` manually in every controller.
*   **Auth Is Enforced Server-Side:** Never rely on the client to gate access to data or actions — every protected endpoint validates the token/session and authorization rules independently, regardless of what the frontend already checked.

```typescript
@UseGuards(AuthGuard('jwt'), RolesGuard)
@Roles('admin')
@Get('users')
async listUsers(@CurrentUser() actor: AuthenticatedUser): Promise<UserResponseDto[]> {
  return this.userService.listAll(actor);
}
```

## 2. Password & Credential Handling

*   **Hash, Never Store Plaintext:** Passwords MUST be hashed with a modern adaptive algorithm (`bcrypt` or `argon2`) using a per-password salt generated by the library itself — never a fixed or reused salt.
*   **Application-Level Pepper:** In addition to the library's per-password salt, apply an application-wide "pepper" (a secret value from environment/secret manager, never in source control) concatenated before hashing, so a stolen password-hash table alone is not enough to brute-force offline.
*   **Never Log Credentials:** Raw passwords, tokens, API keys, and hashes MUST NEVER appear in logs, error messages, or API responses. See [06-logging-data-privacy.md](06-logging-data-privacy.md).
*   **JWT/Session Handling:** Keep access tokens short-lived; use refresh tokens (rotated, revocable) for longer sessions. Sign JWTs with a strong secret or asymmetric key pair sourced from configuration, never hardcoded.

```typescript
const PEPPER = configService.getOrThrow<string>('AUTH_PASSWORD_PEPPER');

async hashPassword(plainPassword: string): Promise<string> {
  return bcrypt.hash(`${plainPassword}${PEPPER}`, 12);
}

async verifyPassword(plainPassword: string, storedHash: string): Promise<boolean> {
  return bcrypt.compare(`${plainPassword}${PEPPER}`, storedHash);
}
```

## 3. Input Sanitization & Trimming

*   **Trim and Sanitize by Default:** All incoming string inputs MUST be trimmed and sanitized against injection/XSS payloads before use (via DTO transform decorators, e.g. `@Transform(({ value }) => value?.trim())`, or a global sanitization pipe).
*   **Password Trimming Is Not Assumed:** Whether password fields should be trimmed is application-specific (a trailing space could be an intentional part of the password). Do not silently trim password inputs — confirm the desired behavior with the user before applying it.
*   **Parameterized Queries Only:** Never build SQL/NoSQL queries via string concatenation or template literals with user input. Use the ORM's parameter binding or query builder exclusively.

## 4. Secrets & Sensitive Files

*   **Never Commit Secrets:** `.env` files, private keys, service account JSON, and credential files MUST NOT be committed. Confirm `.gitignore` covers them.
*   **Warn Before Committing Sensitive Files:** Before any commit, check the staged file list for env files, key material, or anything that looks like a credential/token — even inside an "innocuous" filename — and flag it to the user before proceeding. See [08-agent-workflow-code-quality.md](08-agent-workflow-code-quality.md#6-version-control-hygiene).
*   **Config via `ConfigModule`:** Load and validate environment variables through Nest's `ConfigModule` with a validation schema (`Joi` or `class-validator`) so the app fails fast on startup if a required secret is missing, rather than failing unpredictably at request time.
*   **Treat All Env Values as Sensitive by Default:** Do not print, log, or echo environment variable values while debugging unless the user explicitly confirms the value is non-sensitive.

## 5. Pre-Implementation Security Review

*   **Analyze Before Implementing:** Before writing security-relevant code (auth, payment, PHI/PII handling, file uploads, permissions), analyze the problem against OWASP Top 10 and general industry best practice, and lay out the proposed approach to the user before implementing — see [08-agent-workflow-code-quality.md](08-agent-workflow-code-quality.md#1-pre-implementation-analysis).
*   **Audit-Ready Bar:** The implementation should be defensible to a third-party security auditor — favor well-known, framework-native patterns over clever custom solutions that would need extra justification in a review.

---

## 6. Framework-Provided Security Primitives

*   **`helmet`:** Apply secure HTTP headers via `app.use(helmet())`.
*   **CORS:** Configure `app.enableCors()` with an explicit allow-list of origins — never `origin: '*'` for authenticated APIs.
*   **Rate Limiting:** Use `@nestjs/throttler` for brute-force and abuse protection on sensitive endpoints (login, password reset, OTP verification) rather than a custom counter implementation.
*   **CSRF:** Apply CSRF protection for cookie/session-based flows where applicable; token-based (`Authorization: Bearer`) APIs are typically exempt but should be evaluated case by case.
